# Redis 이벤트 큐 정리 정책

`app.celery.tasks.garbage_collection`은 `queue:*` 스트림을 정리한다.
Celery beat는 기존과 같이 10분마다 실행하며, 기본 유휴 기준은 60초다.

- 실행 시작 시각에서 `timeout_secs`를 뺀 시각을 이번 실행의 고정 기준으로 쓴다.
  마지막 생성 이벤트 ID의 밀리초 부분이 이 기준보다 **작을 때만** 큐를 삭제한다.
  기준과 정확히 같은 이벤트와 미래 시각의 이벤트는 보존한다.
- 보존 정책은 **큐의 유휴 시간**이다. 새 이벤트가 계속 들어오는 큐에서는 이전
  이벤트도 유지한다. 개별 이벤트의 60초 TTL이나 활성 큐 크기 제한은 아니다.
  실제 정리 시점은 beat 실행 주기와 순회 시간에 따라 늦어질 수 있다.
- 빈 스트림도 `last-generated-id`로 판단한다. 한 번도 발행하지 않은
  `0-0` 스트림과 유휴 기준을 넘긴 빈 스트림은 정리하고, 최근 이벤트가 삭제되어
  비어 있는 스트림은 유휴 기준을 넘길 때까지 보존한다.
- 음수 보존 시간은 거부한다. 0은 실행 시작 시각보다 이전에 생성된 큐를 정리한다.

각 큐의 타입 확인, `XINFO STREAM`, 조건부 `UNLINK`를 하나의 Lua 스크립트에서
실행한다. 확인과 삭제 사이에 다른 연결의 `XADD`가 끼어들 수 없다. 발행이
스크립트보다 먼저 실행되면 최신 ID를 확인해 보존하고, 삭제 후 발행되면 새
스트림이 만들어진다. `UNLINK`는 키를 즉시 제거하고 메모리 해제는 비동기로 처리한다.

키 탐색은 `SCAN MATCH queue:* COUNT 100`으로 나누어 실행한다. `COUNT`는 힌트이며
한 페이지 크기의 상한은 아니다. 중복 반환과 중복 GC 실행은 매번 현재 상태를
원자적으로 재확인한다. 탐색 이후 사라진 키와 스트림이 아닌 키는 건너뛴다.
순회 중 새로 만들어진 키는 다음 실행에서 정리될 수 있다.

## 검증

전용 테스트 Redis에서 다음을 실행한다. 기존 backend CI 전체 테스트에도 포함된다.

```sh
docker compose --profile test run --rm test \
  python -m pytest app/tests/service/test_event_gc.py -q
```

테스트는 기존 `XINFO` 직후 발행하던 경쟁을 재현하며, 원자적 처리 직전에도 신규
이벤트를 삽입해 보존을 확인한다. 실제 Redis에서 100개 큐의 300개 이벤트 발행과
두 GC의 동시 실행, 보존 경계, 빈 큐, 중복 순회, 사라진 키를 검증한다.
`TEST_REDIS_URL`은 전용 테스트 Redis만 지정한다. 테스트가 실행하는 GC는 해당 DB의
모든 `queue:*`를 대상으로 한다.

## 합성 부하 측정

2026-11-10에 로컬 Docker 네트워크의 별도 Redis 7.4.11에서 측정했다.
큐 4,000개(유휴 2,000개, 최근 발행 2,000개)와 무관한 문자열 키 10,000개를
매번 새로 만들고, 다른 연결에서 연속 `PING`을 보내면서 GC를 실행했다.
기존 구현과 변경 구현을 각각 3회 실행한 결과의 범위다.

| 구현 | GC 실행 시간 | 동시 PING p99 | 동시 PING 최대 지연 |
| --- | --- | --- | --- |
| 기존 KEYS + XINFO + DELETE | 740–873 ms | 0.254–0.309 ms | 3.507–4.432 ms |
| SCAN + 원자적 조건부 UNLINK | 526–649 ms | 0.206–0.290 ms | 0.559–1.212 ms |

각 실행 후 최근 발행 큐 2,000개가 남는 것을 확인했다. 이 측정은 작은 합성
이벤트를 사용한 로컬 비교이며, 운영 트래픽이나 큰 스트림의 처리량 보장은 아니다.
