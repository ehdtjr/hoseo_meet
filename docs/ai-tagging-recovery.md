# AI 태깅 체크포인트와 재개

AI 태깅은 계속 `AI_ENABLED=false`가 기본이다. 활성화를 위한 실제 유료 AI 호출은
이 변경의 검증에 포함하지 않는다. 배포 시 worker를 시작하기 전에
`alembic upgrade head`로 `20261110_0006`을 적용한다.
기존 API의 메시지 저장 트랜잭션을 drain한 뒤 새 API와 worker를 함께 적용한다.
메시지 저장 잠금 규약을 쓰지 않는 이전 API와 새 worker를 혼용하지 않는다.

## 처리 기준

`user_tagging_checkpoint`는 사용자마다 분석 버전, 상태, 마지막으로 처리한 메시지 ID,
이번 분석의 대화 종료 메시지 ID를 저장한다. `UserTag` 존재 여부로 완료를 판단하지
않는다. 기존 태그만 있고 체크포인트가 없는 사용자는 종료된 대화 전체를 분석하며,
이미 있는 태그와 점수는 유지한다.

최신 메시지에 기존 종료 문구가 있는 사용자 중 다음 조건의 사용자를 처리한다.

- 체크포인트가 없거나 현재 `ANALYSIS_VERSION`과 버전이 다르다.
- 상태가 `pending`, `running`, `failed`이거나 완료 이후 새 대화가 종료되었다.

QA는 기존과 같이 메시지 ID 순서에서 인접한 assistant 질문과 user 답변이다.
메시지 저장은 `ChatBotMessageCRUD.create`에서 사용자별 transaction advisory lock을
먼저 획득하고 INSERT한다. 따라서 같은 사용자의 다음 메시지는 앞선 메시지의 커밋
또는 rollback 후에 ID를 발급받는다. 다른 사용자의 저장은 이 잠금에 막히지 않는다.
직접 SQL로 메시지를 추가하는 이관·관리 도구도 같은 잠금 규약을 적용해야 한다.
각 QA의 태그 저장과 답변 메시지 ID 갱신을 **같은 트랜잭션**으로 커밋한다.
감정 불일치나 중립처럼 정상적인 무태그 결과도 처리 위치를 갱신한다.
미처리 QA가 없으면 종료 메시지 ID까지 커서를 옮기고 `completed`로 기록한다.
QA가 없는 종료 대화도 AI 호출 없이 완료한다.

## 실패와 재시도

HTTP 오류, 감정 분석의 실패·취소·폴링 시간 초과, 누락되거나 잘못된 결과,
허용 목록 밖의 키워드, DB 오류는 모두 현재 QA의 실패다. 정상적인 무태그 결과로
취급하지 않는다. 먼저 세션을 rollback한 뒤 가능한 경우 `failed`와 예외 클래스명만
기록한다. 오류 본문이나 사용자 대화는 체크포인트에 보관하지 않는다.

실패한 사용자는 해당 실행에서 건너뛰고 다음 사용자를 별도 세션으로 처리한다.
기존 3분 주기 작업의 다음 실행에서 실패한 QA부터 다시 시도한다. 영구 실패를
자동 완료하거나 일정 횟수 이후 영구 제외하지 않는다. 지속 실패 시 원인과 외부 서비스
설정을 수정한다. 장애로 실패 상태 기록마저 불가능해도 앞서 커밋한 위치는 유지된다.
worker가 중단되어 `pending`/`running`이 남아도 같은 방식으로 재개한다.

동일 사용자의 QA 처리 중에는 체크포인트 행을 잠근다. 다른 worker는 `SKIP LOCKED`로
바쁜 사용자를 건너뛰며, 매 QA 처리 전에 최신 커서를 다시 읽는다. 서로 다른 사용자가
같은 새 키워드를 저장할 때는 `tag.name`의 기존 unique 제약과 upsert를 사용한다.
최초 체크포인트 생성도 별도 사용자별 `pg_try_advisory_xact_lock` 아래에서 수행한다.
초기화가 진행 중이면 즉시 건너뛰므로 존재 확인과 INSERT 사이의 경쟁에서도 기다리지
않는다. 초기화 잠금은 초기화 commit에서 해제되며 AI 분석 동안 유지하지 않는다.
이 태깅 경로는 체크포인트 행 잠금 아래에서 기존 UserTag를 조회하므로 재처리로 같은
태그를 추가하지 않는다. 과거에 다른 경로로 생성된 중복 UserTag를 삭제하지는 않는다.

QA 조회는 사용자·메시지 ID 인덱스로 다음 질문과 바로 다음 메시지 한 건을 탐색한다.
바로 다음 메시지가 user인 경우에만 QA로 인정하므로 기존 인접 규칙을 유지한다.
QA마다 남은 전체 대화를 Python으로 다시 가져오지 않는다. `20261110_0006`은 이
탐색을 위한 `ix_chat_bot_message_user_id_id` 인덱스도 함께 추가한다.

## 버전과 운영 경계

분석 규칙·프롬프트·후보 목록의 의미를 변경하면 `ANALYSIS_VERSION`을 올린다.
버전이 바뀌면 커서를 처음으로 되돌려 종료된 대화를 재분석하되 기존 태그를 유지한다.
태그 교체·삭제 기능은 제공하지 않는다. 한 시점에 같은 분석 버전의 worker만 운영한다.

커서는 추가되는 메시지의 증가하는 ID를 기준으로 한다. 기존 메시지 내용의 직접 수정은
자동 감지하지 않으며, 재분석이 필요하면 분석 버전을 올린다. DB rollback은 이미 발생한
외부 AI 비용을 취소하지 않는다. AI 응답 후 DB 커밋 전에 중단되면 그 QA의 외부 호출은
다시 실행될 수 있지만 태그와 체크포인트는 부분 저장되지 않는다.

운영 DB에서 downgrade로 체크포인트를 없애지 않는다. 복구는
[DB migration과 백업 복원 절차](database-migrations.md)를 따른다.

## 자동 검증

`backend/app/tests/service/test_tagging.py`는 실제 PostgreSQL 트랜잭션과 AI 대역으로
부분 실패 후 재개, 무태그 결과의 재개, DB 예외의 rollback과 사용자별 세션 격리,
태그 멱등성, 버전 변경, 새 대화, 커밋 응답 손실, 동시 worker, 공통 키워드 생성,
AI 비활성 경로 및 외부 오류 분류를 검증한다. 유료 AI 네트워크 호출은 대역으로 막는다.
최초 생성 직전의 worker 경쟁, 실제 CRUD에서 앞선 답변 commit 지연 시 종료 메시지의
대기, 다른 사용자 쓰기 독립성, 비정형 메시지의 QA 인접성, 100개 QA의 조회 결과 행 수
제한도 회귀 검사한다.

마이그레이션 suite는 이전 `0005` DB의 upgrade 및 adoption, 기존 태그·점수 보존,
빈 DB 재현, 반복 upgrade와 현재 ORM schema 일치를 검증한다.

### 로컬 검증 결과 (2026-11-10)

별도 Compose 프로젝트 `hoseo-issue29-check`의 전용 PostGIS DB와 Redis에서 기존
의존성 이미지에 현재 소스를 읽기 전용 mount해 검증했다.

- 백엔드 전체: **252 passed, 4 warnings, 137.07초**.
- 전체 실행 후 추가한 worker 중단·재개 회귀: **1 passed, 1 warning, 1.33초**.
- 마이그레이션 전체: **29 passed, 8 warnings, 58.18초**.
- 변경 Python 파일 Ruff, Compose 설정, 추적된 credential 검사, `git diff --check` 통과.

경고는 기존 Pydantic 설정 deprecation, 테스트 helper 클래스 수집, admin OpenAPI
operation ID 중복, Alembic computed 기본값 비교에 관한 것이다. 이 결과는 로컬 합성
데이터와 AI 대역 검증이며, 새 이미지 빌드·원격 CI·운영 DB 적용·실제 AI 호출·배포의
증거는 아니다.

### 리뷰 보완 검증 (2026-11-10)

메시지 저장 순서 보장, 최초 체크포인트 생성 경쟁 방지, 다음 QA만 조회하는 쿼리와
인덱스를 반영한 소스를 별도 프로젝트 `hoseo-issue29-review-fixes`에서 검증했다.

- 태깅 회귀 전체: **23 passed, 1 warning, 7.53초**.
- 백엔드 전체: **258 passed, 4 warnings, 135.27초**.
- 마이그레이션 전체: **29 passed, 8 warnings, 52.57초**.
- 변경 Python 파일 Ruff, Compose 설정, 추적된 credential 검사, `git diff --check` 통과.

실제 CRUD의 commit을 답변 ID 발급 뒤 지연시키고 종료 메시지의 advisory lock 대기를
`pg_stat_activity`로 확인했다. 답변 commit 전에는 태깅이 완료되지 않으며, 두 메시지
commit 후 해당 QA를 한 번 분석해 완료한다. 최초 생성 경쟁은 체크포인트 존재 확인과
INSERT 사이를 중단시켜 다른 worker가 즉시 건너뛰는지 검사했다.

100개 QA의 분석에서 DB가 반환한 메시지 행 수를 300개 이하로 제한하는 회귀를
통과했다. 별도 합성 DB에 1만 개 QA를 넣고 처음·중간·마지막 QA 위치에서
`EXPLAIN ANALYZE`를 실행해, 질문과 바로 다음 메시지의 index scan이 각각 1행·1회임을
확인했다. 실제 AI 호출 없이 검증했으며 경고와 배포 검증 경계는 위와 같다.
