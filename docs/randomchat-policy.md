# 랜덤채팅 매칭 정책과 API (#25)

로그인하고 이메일 인증을 완료한 활성 계정 두 명을 **대기 순서(FIFO)**로 연결한다.
사용자는 상대를 지정하지 않는다. 기존 프로필과 채팅 기능을 사용하며 **익명 채팅이 아니다**.
한 계정은 대기 항목 하나 또는 현재 매칭 결과 하나를 가진다. 기존 랜덤채팅방에 참여 중이면
재참가 요청은 같은 방을 반환하며, 그 방에서 나간 뒤 새 매칭을 시작할 수 있다.
성별·태그 등 조건 매칭, 이전 상대 제외, 복수의 동시 랜덤 매칭은 제공하지 않는다.

## 사용자 흐름

앱의 채팅 탭에서 `매칭 시작` → `상대를 찾고 있어요` → `채팅방 열기` 순서로 진행한다.
상대가 이미 기다리고 있으면 즉시 매칭될 수 있다. 먼저 참가한 사용자도 상태 조회를 통해
같은 방 ID를 받으며, 채팅방 목록에 두 사람의 방이 나타난다. 일반 채팅방 열기와 메시지
전송/조회 흐름을 그대로 사용한다. 매칭만으로 화면을 강제로 이동시키지는 않는다.

대기 중에는 `대기 취소`를 사용할 수 있다. 취소가 먼저 처리되면 대기열에서 제거되고,
매칭이 먼저 처리됐으면 취소 성공 대신 매칭된 방을 보여 준다. 방에서 나가기는 기존
채팅방 나가기 기능을 사용한다. 상대가 나가도 자신의 구독은 유지되며, 새 상대를 찾으려면
자신도 방에서 나간 후 다시 참가한다. 이미 나간 랜덤채팅방을 일반 참가 API로 재가입할 수 없다.
매칭 카드 또는 일반 채팅방 목록 중 어느 경로로 입장했든, 방에서 돌아오면 목록과 매칭 상태를
다시 조회한다. 방을 나간 사용자에게는 `매칭 시작`을 표시한다. 복귀 전에 시작된 조회가
진행 중이면 그 요청 이후에 새 상태를 조회해 오래된 매칭 결과가 남지 않게 한다.
채팅방 목록도 최신 요청의 응답만 반영하고 나가기 전에 시작된 조회는 무효화한다.
여러 방을 한꺼번에 나가다가 일부 요청이 실패하거나 응답이 유실돼도, 랜덤방을 선택했다면
목록과 매칭 상태를 다시 확인한다. 상태 재조회에서 매칭 방 ID가 바뀌면 목록도 갱신한다.

## API 계약

기본 prefix는 `/api/v1`이고 모든 경로는 기존 활성·이메일 인증 사용자 인증을 요구한다.
사용자 ID는 인증 세션에서 가져오며 요청 본문으로 다른 사용자를 지정할 수 없다.

| 요청 | 의미 | 200 응답의 status |
| --- | --- | --- |
| `POST /random/match/queue/join` | 대기열 참가 또는 기존 결과 확인 | `waiting`, `matched` |
| `GET /random/match/queue` | 자신의 상태 조회, 유효한 대기의 heartbeat | `idle`, `waiting`, `matched` |
| `POST /random/match/queue/leave` | 대기만 취소; 매칭된 방은 유지 | `idle`, `matched` |

```json
{"status": "waiting", "stream_id": null}
```

```json
{"status": "matched", "stream_id": 123}
```

- `idle`: 현재 대기/활성 매칭이 없음. 대기 취소·만료·이전 방 나가기 후 조회가 여기에 해당한다.
- `waiting`: 참가가 커밋됐고 상대를 기다리는 중. `stream_id`는 null이다.
- `matched`: 방과 Recipient, 두 활성 구독이 모두 커밋됨. `stream_id`는 생성된 `Stream.id`다.
- 반복 참가와 상태 조회는 FIFO 순서를 변경하지 않는다. 매칭 후 재시도도 같은 방 ID를 반환한다.
- 동일 계정의 여러 기기는 같은 상태를 공유한다. 한 기기의 취소는 계정의 대기를 취소한다.
- 서버는 상태 응답을 `Cache-Control: no-store`로 반환한다.
- DB 오류/잠금 대기 초과는 `503`, `detail.code=random_chat_unavailable`을 반환한다.
  민감한 DB 오류 문구를 응답에 넣지 않는다. 미인증 요청은 기존 인증 정책에 따른 `401`이며,
  참가 직전 계정의 활성/인증 자격을 잃으면 `403`이다.

## 대기 유지와 복구

대기 유효기간은 마지막 성공한 참가 또는 상태 조회 이후 **90초**다. 앱은 대기 중
약 **5초 간격**으로 상태를 확인한다. 앱이 백그라운드로 가면 폴링을 중단하고, 복귀 시
상태를 다시 조회한다. 다른 탭으로 이동해도 폴링을 중단하며 채팅 탭 복귀 시 재조회한다.
앱 종료나 통신 단절로 heartbeat가 없으면 대기가 만료된다.
만료된 사용자는 매칭되지 않으며 새 참가 요청이 있어야 다시 대기한다.
앱을 켜거나 채팅 탭에 들어오는 것만으로 자동 참가하지 않는다.

조회·재시도는 서버 상태를 기준으로 화면을 복구한다. 통신 실패를 취소나 매칭 성공으로
간주하지 않는다. 참가 응답이 유실되어도 GET으로 대기/매칭 상태를 복구할 수 있고,
취소 응답이 유실되어도 GET으로 취소 여부 또는 먼저 완료된 매칭을 확인할 수 있다.
상태 조회에 실패하면 마지막 대기/매칭 결과를 확정 상태로 표시하지 않고
`매칭 상태를 확인하지 못했어요`와 `다시 확인` 버튼을 계속 표시한다. 활성 채팅 탭에서는
약 5초 간격의 자동 재확인도 이어가며, 성공한 응답으로 현재 상태를 복구한다.
주기적 조회 실패마다 스낵바를 반복하지는 않는다. 90초 이상 통신이 끊겼어도 대기 중이라고
표시하지 않으며, 만료 후에는 다시 참가해야 한다.

## 저장소와 트랜잭션

**대기열의 기준 저장소는 PostgreSQL**의 `random_chat_queue`다. Redis의 기존
미완성 `waiting_room` 큐는 사용하지 않는다. Redis는 기존 메시지/WebSocket 전달에 사용하며,
대기열을 Redis와 DB에 이중 기록하지 않는다. 이전 Redis 키를 자동 삭제하거나 이관하지 않는다.

- `user_id` 기본키가 사용자별 대기/결과 중복을 막는다. 대기 시간, 만료 시간, 매칭된 방 ID를 저장한다.
- 참가·조회·취소는 공통 PostgreSQL transaction advisory lock으로 직렬화한다.
  여러 API 프로세스에서도 같은 잠금을 사용하며, commit/rollback/연결 종료 시 해제된다.
- 잠금 대기 한도는 5초다. 이 방식은 작은 규모의 1:1 매칭을 위한 단순한 일관성 설계다.
  처리량이 커지면 실제 부하 측정 후 큐 분할 등을 별도로 설계한다.
- 참가 자격을 확인하는 사용자 행은 공유 잠금으로 보호해 매칭 중 관리자 변경과 경합을 제어한다.
- 방·Recipient·두 Subscription·양측 큐 결과를 **하나의 트랜잭션**에서 저장한다.
  각 단계에서 commit하는 일반 Stream/Subscriber CRUD를 호출하지 않는다.
- 중간 단계나 커밋이 실패하면 전체를 rollback한다. **이전에 참가가 성공한 대기자는 보존**되고,
  실패한 새 참가 요청의 입장은 확정되지 않는다. 호출자는 상태 확인 후 재시도한다.
- 커밋은 성공했지만 HTTP 응답이 유실된 경우, 영속화된 결과를 읽어 같은 방을 반환한다.
  프로세스 종료 중 미커밋 트랜잭션은 DB가 rollback하므로 큐에서 꺼낸 사용자만 사라지지 않는다.
- 매칭된 방의 일반 참가/재가입 API는 차단한다. 두 구독은 매칭 트랜잭션만 생성한다.

## 기존 DB 적용

새 빈 로컬/테스트 DB는 모델 등록으로 `Base.metadata.create_all` 시 새 테이블을 함께 생성한다.
기존 DB는 **새 API를 띄우기 전에**, 대상 DB 설정을 사용해 아래 전용 명령을 실행해야 한다.
저장소에 버전 관리된 Alembic 기준 revision이 없어 새 루트 revision을 임의로 만들지 않았다.

```sh
# Compose: 기존 user/streams 테이블이 있는 DB에 대기열 테이블만 추가
# 먼저 현재 소스로 backend 이미지를 빌드해야 한다.
docker compose build web
docker compose run --rm --no-deps web python -m app.scripts.migrate_randomchat
```

명령은 `random_chat_queue` 및 인덱스·외래키만 추가한다. 기존 사용자/채팅 데이터를 변경하지
않으며 동일 스키마에서 재실행해도 큐를 지우지 않는다. 빈 DB 전체 초기화나 이후 스키마
변경을 자동 처리하는 범용 마이그레이션 명령은 아니다. 애플리케이션 롤백 시 추가 테이블은
보존한다. 테이블 삭제는 모든 매칭 API를 중단하고 대기/결과 데이터 폐기를 결정한 뒤 별도로 한다.
과거 공개 API로 수동 생성한 `type=random` 방과 구독은 자동 이관하지 않는다. 기존 DB에
그런 방이 있다면 배포 전 확인해야 하며, 새 대기열의 중복 매칭 제한은 이 매칭 API가 관리하는
결과를 기준으로 한다.

## 검증 범위

백엔드는 실제 PostGIS 테스트 DB에서 두 사용자 매칭, FIFO·중복·동시 요청, 취소 경합,
대기 만료, 부분 DB 실패 rollback/재시도, 이전 방 나가기 후 재참가를 검증한다.
HTTP 계약과 인증, 매칭 외 일반 참가 차단도 확인한다. 앱은 HTTP 응답 처리와 대기·매칭·취소,
통신 실패 복구 및 생명주기 동작을 테스트한다.

```sh
docker compose --profile test run --rm test
# Flutter 3.32.1 / Dart 3.8.1
cd frontend/app
flutter test --no-pub
```

### 로컬 실행 결과

- 백엔드 전체 **142 passed**. 전용 PostGIS·Redis, 현재 소스 마운트로 실행했다.
- 신규 백엔드 집중 **20 passed**: 실제 JWT 로그인 → 매칭 → 텍스트 송수신·위치 권한,
  동시 참가/취소/만료, 부분 실패, 기존 DB 업그레이드와 재실행 시 데이터 보존을 포함한다.
- 부분 실패 테스트를 실제 PostgreSQL 오류(`SELECT 1 / 0`)로 강화한 후 해당 테스트도
  **1 passed**로 재검증했다. 부분적으로 생성한 방·구독은 rollback되고 기존 대기자는 보존된다.
- Flutter 3.32.1 전체 **94 passed**. 이 중 랜덤채팅·목록 경합 관련 테스트 **24개**가 통과했다.
  실제 ChatPage 위젯의
  참가 → 폴링 → 매칭 → 방 진입, 취소 경합/실패, 응답 유실, 탭 전환·dispose를 검증했다.
  리뷰 회귀 테스트로 일반 목록 → 방 나가기 → 재참가, 100초간 조회 실패와 상태 확인 불가 표시,
  재조회 복구, 방 복귀 전 오래된 요청과 취소 후 늦은 실패 응답의 경합을 추가 검증했다.
  목록 응답 역전과 단일·일괄 나가기 후 오래된 목록 응답, 일괄 나가기 부분 실패/응답 유실,
  상태 재조회에서 매칭 방 ID 변경 시 목록 갱신도 검증했다.
  HTTP 통합 테스트와 Flutter 위젯 테스트는 각각 실행했으며 실제 기기 통합 E2E는 아니다.
- 변경 Flutter 파일 분석과 디버그 번들 빌드 통과, lockfile 변경 없음.
- 신규 Python 코드·테스트 Ruff 검사와 CRLF를 고려한 diff 공백 검사 통과.
- 백엔드의 기존 Pydantic 설정·테스트 클래스 수집·관리자 OpenAPI operation ID 경고는 남아 있다.

CI, APK/IPA, 운영 배포, 실기기 검증은 수행하지 않았다. 기존 DB 마이그레이션 역시
위 전용 테스트 DB에서만 검증했고 운영 DB에는 적용하지 않았다.
