# 채팅 전송과 재전송 계약 (#21)

## 현재 클라이언트

- 논리적 전송마다 UUID v4 `clientMessageId`를 만들고 `X-Client-Message-ID` 헤더로 보낸다. `POST /api/v1/messages/send/stream/{stream_id}`의 `message_content`는 기존 form-urlencoded 형식을 유지한다.
- 로컬 전송 상태는 `sending → 성공 시 제거` 또는 `sending → failed`다. 실제 메시지는 서버 ID를 가진 WebSocket 이벤트/메시지 조회 결과로 표시하며 서버 ID로 병합한다. HTTP 2xx만 전송 성공이다. 실패한 본문과 ID는 명시적 재전송까지 보관하며, 같은 실패 초안을 전송 버튼으로 다시 보내도 ID를 재사용한다.
- 전송 중에는 한 요청만 허용한다. 성공한 초안은 전송 시작 이후 편집되지 않은 경우에만 입력창에서 지운다. 새 초안과 실패한 원문은 각각 보관하므로 원문 재전송이 새 입력을 덮어쓰지 않는다.
- HTTP 401에 한해 토큰 갱신 후 한 번 재시도한다. 메서드, URL, 사용자 헤더, 인코딩된 본문 바이트와 Content-Type을 보존하며 Authorization만 바꾼다. multipart는 파일·필드·boundary를 포함한 본문을 임시 파일에 스트리밍해 보관하고, 각 시도에서 그 파일을 다시 스트리밍한다. 전체 업로드를 RAM에 적재하지 않으며 완료·실패 후 임시 파일을 정리한다. 임의의 스트리밍 요청은 자동 재전송하지 않는다.
- 통신 오류/4xx/5xx에는 자동 메시지 재전송을 하지 않는다. 실패 상태와 원문을 표시하고 사용자가 재전송을 선택한다. 성공 후 최신 메시지를 조회하며, 이 조회 실패를 메시지 전송 실패로 취급하지 않는다. 소켓에서 놓친 메시지를 복구하면 조회한 ID 범위만 서버에서 읽음 처리하고, 해당 범위의 최신 미읽음 수와 채팅방 목록의 마지막 메시지·시간을 갱신한다. 읽음 응답 실패도 성공한 메시지의 재전송을 유발하지 않으며, 방을 닫은 뒤 도착한 조회 응답은 읽음 처리하지 않는다.

## 서버 중복 방지 연동 계약

서버는 `X-Client-Message-ID`를 저장하고 인증된 `(sender_id, client_message_id)`를 고유 키로 사용한다. UUID를 다른 방에서 재사용해도 별도 전송으로 처리하지 않으며 `409 Conflict`로 거절한다. 키는 메시지가 보존되는 동안 유지한다.

1. 같은 키·방·본문의 재전송은 기존 `message_id`와 현재 전달 상태를 반환한다. 본문, 수신 상태, outbox를 추가 생성하지 않는다. 다른 방 또는 본문에 같은 키를 사용하면 409다.
2. HTTP 200은 `storage_status=saved`를 뜻한다. 신규 저장은 `delivery_status=pending`, 재전송은 실제 outbox 상태에 따라 `pending` 또는 `completed`다. 외부 전달 실패 때문에 이미 저장한 메시지를 HTTP 실패로 돌리지 않는다.
3. 성공 응답은 `message_id`, `client_message_id`, `duplicate`를 포함한다. WebSocket·FCM의 메시지 payload와 HTTP 메시지 조회에도 `client_message_id`를 포함한다. 기존 메시지는 null이다.
4. 구버전 클라이언트의 헤더 없는 요청에는 서버가 ID를 생성한다. 이 경우 응답을 잃고 ID 없이 재전송하면 중복 방지를 보장할 수 없다. 새 앱은 기존 UUID 헤더를 유지한다.
5. DB 저장 확인 실패는 503이며 반드시 같은 ID로 재시도한다. 프로세스 중단·응답 유실 시에도 저장 여부는 이 재시도로 확인할 수 있다.

본문·수신 상태·수신자별 outbox는 한 트랜잭션으로 저장한다. 전달 재시도는 메시지를 다시 저장하지 않는다. Redis/FCM 전송 자체는 at-least-once이며 프로세스 중단 시 외부 알림의 중복 가능성은 남는다. [서버 재처리·마이그레이션·검증 절차](message-outbox.md)를 참고한다.

로컬 보류 메시지는 해당 provider의 메모리에 보관된다. 앱 재시작을 넘는 클라이언트 영구 outbox와 기기-서버 E2E는 이 변경에 포함되지 않는다.

## 로컬 검증

CI와 같은 Flutter 3.32.1 / Dart 3.8.1에서 기존 `pubspec.lock`을 사용한 `flutter pub get --enforce-lockfile`, 테스트 42개, `flutter build bundle --debug --no-pub`가 통과했다. 변경 파일 정적 분석은 오류·경고 없이 기존 안내 4건(간접 의존성 import 3건, 위치 API deprecation 1건)을 보고했다. 저장소의 lockfile과 분석 설정은 변경하지 않았다. GitHub CI 실행 및 기기-서버 E2E 결과는 별도 확인이 필요하다.

추가 회귀 검증은 다음을 포함한다.

- 소켓 없이 복구한 메시지의 서버 읽음 처리, 다른 참여자의 미읽음 수 보존, 목록의 마지막 메시지·시간 갱신.
- ID에 고정한 읽음 범위 밖의 새 메시지 보호, 읽음 응답 실패 시 전송 성공 유지, 방 종료 후 늦은 조회 응답 무시.
- 64MiB 파일을 64KiB 이하 청크로 스트리밍하고, 첫 전송 후 원본 파일을 삭제해도 인증 재시도에서 같은 본문 길이와 boundary 유지.
- 단일·다중 multipart의 바이트 보존 및 HTTP 실패·통신 실패·인증 갱신 실패 시 임시 파일 정리.
